# 机场服务端对接指南（v2）

本文面向机场/服务商的服务端开发人员。v2 协议对应客户端 spec：`cpx-plugin/2`。

相关文件：

- 参考服务端：[`deploy/gateway/`](../../deploy/gateway/)（部署、环境变量、`cpx-admin` 命令见
  [`deploy/gateway/README.md`](../../deploy/gateway/README.md)）
- 描述文件生成脚本：[`scripts/plugin/gen-cpx.mjs`](../../scripts/plugin/gen-cpx.mjs)
- 英文版：[`PROVIDER_INTEGRATION_v2.md`](PROVIDER_INTEGRATION_v2.md)

> ## 本改造版说明（与上游 v2 设计的差异）
>
> 本仓库是 Clash Party 的**内网直连改造版**。与上游 `cpx-plugin/2` 设计相比：
>
> - **已移除请求签名**。没有 Ed25519 设备密钥，`/enroll` 不带 `devicePubKey`，
>   `/config` 与 `/revoke` 不带 `sig`、`ts`。设备身份 = `deviceId` + 一次性 nonce（第 11 节）。
> - **本地凭据不加密**。客户端把 `deviceId` 和缓存网关以明文 JSON 落盘。
> - **允许 `http://` 与内网 host**：`loginUrl` 和 `gateway` 都可为 `http`，可为
>   `127.0.0.1`、内网 IP、`localhost`。`IP:port` 部署不需要域名和证书。
> - **已移除深链与文件关联**。`clash://install-plugin?url=...` 无实现，双击 `.cpx`
>   也不会启动任何东西（桌面壳已移除）。插件导入改在 Web UI 内完成（第 3 节）。
> - **上游签名测试向量在本版中不存在**：`src/main/resolve/plugin/__fixtures__/sign-vectors.json`
>   已被删除。
>
> `spec` 字符串仍为 `cpx-plugin/2`，但线上语义以本文为准。请按本文实现，
> 不要按上游 v2 规格实现。本版面向可信内网，不要暴露到不可信网络。
>
> 开发过程中曾有一版 v1 方案（账号密码 + 加密容器）。该方案已弃用，当前代码库未包含 v1 实现。

## 1. 接入模型

v2 不把真实订阅 URL 或 API 域名写入客户端文件。用户导入的 `.cpx` 只包含登录入口和服务商展示信息；登录在浏览器中打到服务商自己的页面；客户端本地生成 `deviceId`（UUIDv4），该 id 加一次性 nonce 就是全部设备凭据；后续订阅更新通过网关的 challenge/config 流程完成。

服务端需要提供三类能力：

| 模块                       | 所在域名                                  | 用途                                   |
| -------------------------- | ----------------------------------------- | -------------------------------------- |
| OAuth authorize 登录页     | 登录域名，即 `.cpx` 中 `loginUrl` 的 host | 用户登录，签发一次性 `code`            |
| `/.well-known/cpx-gateway` | 同登录域名、同端口                        | 返回当前网关 origin 和端点路径         |
| 网关端点                   | 网关域名，可与登录域名不同                | 设备注册、发放 nonce、拉订阅、解绑设备 |

登录域名是信任根，会固化在已经发出的 `.cpx` 文件中；网关域名由 `/.well-known/cpx-gateway` 动态发现，可以替换。

| 故障位置   | 影响                                                               |
| ---------- | ------------------------------------------------------------------ |
| 网关域名   | 客户端可经登录域名重新发现新网关                                   |
| 登录域名   | 已登录设备可继续访问现有网关；无法新登录、重登，也无法重新发现网关 |
| 两者都故障 | 客户端失联，需要重新分发新的 `.cpx`                                |

端到端流程：

```text
安装：
  在 Web UI 中导入 .cpx（拖到订阅页，或插件卡「导入插件」→「选择文件」）
  客户端校验描述文件，创建本地记录（status=needs-login），不联网

登录：
  1. GET {loginUrl 协议}://{loginUrl host}/.well-known/cpx-gateway
  2. 客户端生成 deviceId(UUIDv4)
  3. 浏览器打开 authorize URL：
     loginUrl?response_type=code&code_challenge=...&state=...
     客户端不会自动打开浏览器——它把授权 URL 写入应用日志（终端输出与日志文件）后等待（见第 4 节）
  4. 用户在服务端页面登录，服务端 302 回
     http://127.0.0.1:<port>/callback?code=...&state=...
  5. POST {gateway}/enroll，用 code 和 PKCE verifier 注册设备
  6. POST {gateway}/challenge，领取一次性 nonce
  7. POST {gateway}/config，带 deviceId 和 nonce 拉取 Clash YAML
  8. 客户端把 YAML 落成普通订阅 profile

更新：
  按插件间隔（默认 24 小时）重复 challenge -> config，不再打开浏览器

重新登录：
  服务端返回 {"error":"revoked"} 或 {"error":"device_revoked"}
  客户端标记为 needs-reauth，用户重新走登录流程

删除：
  客户端尽力调用 /revoke，然后删除本地记录
```

## 3. `.cpx` 文件

`.cpx` 是公开 JSON 文件，不包含用户信息、token、API host 或订阅 URL。所有用户可以使用同一份文件。

```json
{
  "magic": "CPXF",
  "v": 2,
  "spec": "cpx-plugin/2",
  "loginUrl": "http://192.168.1.10:8080/oauth/authorize",
  "provider": {
    "name": "Example 机场",
    "icon": "data:image/png;base64,iVBORw0K...",
    "site": "http://example.lan"
  }
}
```

字段要求：

| 字段            | 要求                                                                                                            |
| --------------- | --------------------------------------------------------------------------------------------------------------- |
| `magic`         | 字符串 `"CPXF"`                                                                                                 |
| `v`             | 数字 `2`                                                                                                        |
| `spec`          | 字符串 `"cpx-plugin/2"`                                                                                         |
| 顶层字段        | 只能包含 `magic`、`v`、`spec`、`loginUrl`、`provider`                                                           |
| `loginUrl`      | `http` 或 `https` URL；不能包含 query、fragment、userinfo；host 不限制，私网 IP、`127.0.0.1`、`localhost` 均可  |
| `provider`      | 对象，只能包含 `name`、`icon`、`site`                                                                           |
| `provider.name` | 必填，非空字符串                                                                                                |
| `provider.icon` | 可选；仅支持 `data:image/png;base64,`、`data:image/jpeg;base64,`、`data:image/webp;base64,`；总长度不超过 65536 |
| `provider.site` | 可选；`http`/`https` URL；不能含 userinfo；可包含路径和 query                                                   |

`loginUrl` 必须是 authorize 端点，不是普通登录首页。客户端会在该 URL 后拼接 OAuth 参数。

`v: 1` 的文件会被单独拒绝，提示"插件文件格式过旧，请向机场索取新文件"。

生成脚本：

```bash
node scripts/plugin/gen-cpx.mjs http://192.168.1.10:8080/oauth/authorize "Your Airport" http://192.168.1.10:8080 your-airport.cpx
```

脚本只写 `loginUrl`、`provider.name` 和（可选的）`provider.site`。需要图标请手工补 `provider.icon`。

### 分发方式

导入在 Web UI 内完成：

- 把 `.cpx` 拖到订阅页，或用插件卡的「导入插件」按钮「选择文件 (.cpx)」。
- 客户端会先显示预览确认页（机场名、图标、官网、登录域名）。预览与安装阶段不联网，第一次网络请求发生在用户点「登录」时。
- 描述文件超过 1 MiB 会被客户端拒绝。

本版**没有深链**：`clash://install-plugin?url=...`、`mihomo://` 均无实现，注册 `.cpx` 文件关联也没有任何效果。请把描述文件提供下载，让用户在 Web UI 里导入。

## 4. OAuth authorize

登录流程使用 OAuth 2.0 Authorization Code + PKCE(S256)。密码只提交到服务商页面，客户端不接触密码。

客户端请求参数：

| 参数                    | 值                                             |
| ----------------------- | ---------------------------------------------- |
| `response_type`         | `code`                                         |
| `client_id`             | `mihomo-party`                                 |
| `redirect_uri`          | `http://127.0.0.1:<random-port>/callback`      |
| `code_challenge`        | `BASE64URL(SHA256(code_verifier))`，无 padding |
| `code_challenge_method` | `S256`                                         |
| `state`                 | 随机串，服务端必须原样带回                     |
| `scope`                 | `subscribe`                                    |

authorize 端点要求：

1. 允许 `http://127.0.0.1:<random-port>/callback` 形式的回环重定向。端口每次登录随机，不能按固定端口白名单处理。参考实现接受 `^http://(127\.0\.0\.1|localhost):\d{1,5}/callback$`。
2. 用户登录成功后，`302` 到 `redirect_uri?code=...&state=...`。
3. `code` 必须一次性、短 TTL（不超过 60 秒）。
4. 签发 `code` 时记录 `username`、`redirect_uri`、`client_id`、`code_challenge`。`/enroll` 时逐字节比对 `redirect_uri` 与 `client_id`。
5. 对登录尝试限流。参考实现按 IP 限制 60 秒内 10 次 authorize POST，超出返回 429 错误页。

原生应用的 loopback redirect 允许使用 HTTP，依据 RFC 8252。不要因为 `redirect_uri` 不是 HTTPS 而拒绝。

### 客户端实际怎么打开这个 URL

客户端不会启动浏览器。它生成 authorize URL 后写入 Clash Party 应用日志，然后最多等 5 分钟的回调。日志行形如：

```text
[<时间戳>] [WARN] [PluginOAuth] open in your browser: http://<login-host>/oauth/authorize?...
```

该行同时出现在进程终端输出和**数据目录下的 `logs/clash-party-<日期>.log`**，因此 `docker logs` 和日志文件都能取到。用户从日志复制该地址到浏览器打开；Web UI 的提示文案也是这么写的，不承诺自动打开浏览器。

回环回调监听在**运行客户端的那台机器的 `127.0.0.1`** 上。因此完成登录的浏览器必须能访问该地址，即满足下列之一：

- 浏览器与客户端在同一台机器上；或
- 端口被转发（SSH 隧道），或部署上把浏览器所在机器的 `127.0.0.1:<port>/callback` 路由到客户端所在机器。

浏览器在另一台机器且没有隧道时，服务端的 302 回不到任何监听者，登录无法完成。建议服务商在自己的登录页上把 authorize URL（或二维码）显示出来，便于运维换到满足条件的浏览器上完成。

回调 `state` 不匹配或缺 `code` 时，客户端页面显示 `Login failed. You may close this window.`；成功时显示 `Login complete. You may close this window.`。

## 5. 网关发现

客户端按 `loginUrl` 的精确 host 请求，协议沿用 `loginUrl`：

```text
GET {loginUrl 协议}://{loginUrl host}/.well-known/cpx-gateway
```

响应体：

```json
{
  "spec": "cpx-plugin/2",
  "gateway": "http://192.168.1.10:8080",
  "endpoints": {
    "enroll": "/enroll",
    "challenge": "/challenge",
    "config": "/config",
    "revoke": "/revoke"
  }
}
```

字段要求：

| 字段        | 要求                                                                                                                                |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `spec`      | 字符串 `"cpx-plugin/2"`                                                                                                             |
| `gateway`   | `http`/`https` origin，仅包含 scheme、host、可选 port；不能有 path、query、fragment、userinfo；host 不限制，私网/环回地址均可       |
| `endpoints` | 必须包含 `enroll`、`challenge`、`config`、`revoke`；每个值是以 `/` 开头的相对路径，不能是绝对 URL、协议相对 `//`、`?`、`#` 或反斜杠 |

客户端请求 `/.well-known/cpx-gateway` 时不跟随重定向，响应体上限 64 KiB。非 2xx、JSON 非法、字段校验失败均视为发现失败。

### 网关轮换

替换网关时，更新 `/.well-known/cpx-gateway` 中的 `gateway` 即可。客户端在下列情况会回到登录域名重新发现，并重试一次：

- 当前网关返回 HTTP `410`；
- 响应 JSON 为 `{"error":"gateway_retired"}`；
- 当前网关发生网络层不可达，例如 DNS 失败、连接失败、TLS 握手失败。

重新发现成功后，客户端会把新网关写回本地 vault，之后的更新直接走新域名。

普通 5xx、429、超时不会触发重新发现，客户端按瞬时故障退避重试。

重新发现依赖登录域名可用。登录域名故障时，已缓存网关仍可继续使用，但无法切换到新网关。删除插件时的解绑也走同一条重新发现路径，因此轮换网关后设备仍能被解绑。

## 6. 网关公共约定

四个端点均为 `POST`，请求体为 JSON，带 `Content-Type: application/json`。客户端按发现结果使用 `http` 或 `https`，不跟随重定向，响应体上限 10 MiB；请求超时取自客户端的订阅超时设置（默认 30 秒）。插件卡上的「走代理」开关可让这些请求经过客户端本地混合代理。

不使用 Authorization header，不下发 bearer token。设备身份由 `deviceId` 和一次性 nonce 确认，没有请求签名。

错误信号按以下优先级处理：

| 客户端判定  | 条件                                                       | 客户端行为               |
| ----------- | ---------------------------------------------------------- | ------------------------ |
| `retired`   | HTTP `410`，或 JSON `{"error":"gateway_retired"}`          | 重新发现网关并重试一次   |
| `revoked`   | JSON `{"error":"revoked"}` 或 `{"error":"device_revoked"}` | 标记为需要重新登录       |
| `transient` | 其它非 2xx（含 `429`）、超时、网络错误                     | 退避重试，不改变登录状态 |
| 成功        | 2xx 且没有错误标记                                         | 正常处理                 |

账号到期、设备被踢、用户被禁用时，返回体必须包含 `revoked` 或 `device_revoked`。单独返回空的 `401`/`403` 会被客户端当作瞬时失败处理。

订阅更新的瞬时失败按指数退避重试：首次失败后 10 分钟，此后每次翻倍，上限 24 小时，另加最多 30% 抖动。

## 7. `POST {gateway}/enroll`

作用：用 authorize 阶段签发的 code 注册设备，相当于 OAuth token exchange，但不返回 bearer token。

请求体：

```json
{
  "code": "<authorize code>",
  "code_verifier": "<PKCE verifier>",
  "redirect_uri": "http://127.0.0.1:<port>/callback",
  "client_id": "mihomo-party",
  "deviceId": "<UUIDv4>"
}
```

服务端处理：

1. 查找 `code`；即使后续步骤失败也要把它消费掉。
2. 校验 `code_verifier`：`BASE64URL(SHA256(code_verifier))` 必须等于签发 code 时保存的 `code_challenge`。
3. 校验 `redirect_uri`、`client_id` 与签发 code 时保存的值逐字节一致。
4. 校验 `deviceId` 是 UUIDv4。
5. 从 `code` 关联到用户。
6. 检查设备数上限，保存设备绑定 `(username, deviceId, created_at)`。
7. 返回 2xx，例如 `{"ok":true}`。

参考实现的错误体：

| 状态 | 响应体                         | 原因                                 |
| ---- | ------------------------------ | ------------------------------------ |
| 400  | `{"error":"invalid_code"}`     | code 不存在、已过期或已使用          |
| 400  | `{"error":"bad_pkce"}`         | verifier 与 challenge 不匹配         |
| 400  | `{"error":"binding_mismatch"}` | `redirect_uri` 或 `client_id` 不一致 |
| 400  | `{"error":"bad_request"}`      | `deviceId` 不是 UUIDv4               |
| 403  | `{"error":"device_limit"}`     | 设备数已达上限                       |

注意：

- `deviceId` 由客户端生成，服务端不要替换。
- 一个用户可绑定多台设备，建议设置设备数上限和清理策略；把已存在的 `deviceId` 重新绑定到同一用户不应再占一个新名额。
- enroll 成功后，即使首次 config 失败，该设备绑定仍然有效。客户端会保留设备并在下次登录尝试时重拉。
- 用户重新登录会生成新的 `deviceId`，也会产生新的设备绑定。

## 8. `POST {gateway}/challenge`

作用：为指定设备发放一次性 nonce。

请求体：

```json
{ "deviceId": "<UUIDv4>" }
```

成功响应：

```json
{
  "nonceId": "<opaque id>",
  "nonce": "<base64 32 bytes>",
  "exp": 60
}
```

要求：

- 按 `deviceId` 维护待用 nonce 池，允许并发存在多个 nonce。
- nonce 为 32 字节安全随机数。
- TTL 建议不超过 60 秒。
- nonce 用完即删；过期定期清理。
- 每个设备的待用 nonce 数应设置上限，例如 8 个。
- `nonceId` 是不透明句柄，可见 ASCII，长度不超过 64，不能包含空格或控制字符。
- `nonce` 使用标准 base64，带 `=` padding；解码后必须正好 32 字节。
- `exp` 只是提示，单位为秒，客户端不强依赖。

参考实现的取值：`nonceId` 为 16 随机字节的十六进制（32 字符），`nonce` 为 32 随机字节的标准 base64（44 字符），TTL 60 秒，池只在内存中——重启即丢弃在途 challenge。

错误：

| 状态 | 响应体                        | 原因                             |
| ---- | ----------------------------- | -------------------------------- |
| 410  | `{"error":"gateway_retired"}` | 网关已退役                       |
| 403  | `{"error":"device_revoked"}`  | 设备不存在、账号到期或设备已吊销 |
| 429  | `{"error":"too_many_nonces"}` | 该设备待用 nonce 数达上限        |

---

## 9. `POST {gateway}/config`

作用：为持有有效 nonce 的设备返回该用户的 Clash YAML。

请求体：

```json
{
  "deviceId": "<UUIDv4>",
  "nonceId": "<challenge nonceId>",
  "nonce": "<challenge nonce>"
}
```

服务端处理：

1. 网关已退役时返回 `410 {"error":"gateway_retired"}`。
2. 查找设备；不存在返回 `403 {"error":"device_revoked"}`。
3. 按 `deviceId`、`nonceId` 查找待用 nonce，常数时间比对 `nonce`；失败返回 `401 {"error":"bad_nonce"}`。
4. 消费 nonce。
5. 由设备关联到用户。
6. 内部生成订阅或从隐藏 origin 拉取。
7. 返回 HTTP 200，body 为 Clash YAML 文本（`text/yaml; charset=utf-8`）。

客户端每次 `/config` 和 `/revoke` 都会先调一次 `/challenge`，因此每个 nonce 只绑定一次操作。

成功响应不是 JSON。客户端会把 body 当作 Clash 配置解析，要求 YAML 可解析为对象，并且至少包含 `proxies` 或 `proxy-providers` 之一；否则按瞬时失败处理。

订阅 URL、origin API、内部鉴权 token 不应下发给客户端。

隐藏 origin 拉取失败建议返回 `502 {"error":"upstream"}`（参考实现即如此）。

---

## 10. `POST {gateway}/revoke`

作用：解绑设备。客户端删除插件或删除生成的订阅时会尽力调用该端点。

请求体同 `/config`：

```json
{
  "deviceId": "<UUIDv4>",
  "nonceId": "<challenge nonceId>",
  "nonce": "<challenge nonce>"
}
```

处理流程同 `/config`：验 nonce、消费 nonce，然后删除该 `deviceId` 的绑定记录。

`/revoke` 必须幂等。设备已经不存在时仍返回 2xx——参考实现先查设备，此时直接回 `{"ok":true}`，不触碰 nonce 池。

## 11. 设备身份与防重放

本版没有请求签名。设备身份与保护来自两样东西：

- `deviceId`：客户端生成的 UUIDv4，服务端把它绑到某个用户。它是唯一的设备凭据，除"不可猜"之外没有其他保密性。
- 一次性 nonce：每次 `/config`、`/revoke` 之前立刻向 `/challenge` 领取，服务端查池校验后消费一次。

由此得到的性质：

- 请求只在 nonce TTL 内被接受（不超过 60 秒）。
- 重放抓到的请求会失败，因为 nonce 已被消费。
- 客户端不发 bearer token，线路上没有可长期窃取的凭据。

不提供的性质：**调用方身份认证**。任何知道 `deviceId` 的人都能领一个 nonce 并拉走该设备的订阅。因此请把 `deviceId` 和网关都视为内网内部信息——这正是本版的部署前提。

作为对比，上游 v2 设计用 Ed25519 设备密钥对每个请求签名，签名输入为：

```text
SignInput = "CPX2" | uint8(op) | uint8(len(deviceId)) | deviceId
          | uint8(len(nonceId)) | nonceId | nonce(32 原始字节) | uint64_be(ts)
```

`/config` 用 `op=1`，`/revoke` 用 `op=2`，并额外传输 `devicePubKey`、`ts`、`sig`。
**本版既不发送也不校验这些字段。** 要求签名的服务端会拒绝本客户端的所有请求；本客户端也会忽略签名相关字段。请改为实现上面的 nonce 校验。

## 12. 编码规则

| 字段                               | 编码                                                                           |
| ---------------------------------- | ------------------------------------------------------------------------------ |
| `deviceId`                         | UUIDv4，36 字符，小写带连字符；参考实现只接受严格 UUIDv4                       |
| `nonceId`                          | 服务端生成的不透明可见 ASCII，长度不超过 64（参考实现：32 位十六进制）         |
| `nonce`                            | 32 原始字节，标准 base64，带 padding，通常 44 字符                             |
| `code`                             | authorize 签发的不透明字符串；参考实现为 32 随机字节的 base64url（43 字符）    |
| `code_challenge` / `code_verifier` | RFC 7636 base64url，无 padding；verifier 长度 43-128，字符集 `[A-Za-z0-9-._~]` |
| `redirect_uri`                     | `http://127.0.0.1:<port>/callback`                                             |
| `client_id`                        | `mihomo-party`                                                                 |
| `exp`                              | 整数秒；仅作提示                                                               |

除 PKCE 字段外一律用标准 base64（带 `=` padding），不要混用 base64url。签名协议字段（`devicePubKey`、`sig`、`ts`、`op`）本版不使用。

## 13. PHP 参考代码

以下片段只展示关键校验。生产代码仍需补齐参数校验、nonce 状态、用户状态和错误处理。

PKCE：

```php
function pkce_ok(string $verifier, string $challenge): bool {
    $calc = rtrim(strtr(base64_encode(hash('sha256', $verifier, true)), '+/', '-_'), '=');
    return hash_equals($challenge, $calc);
}
```

`/config` 与 `/revoke` 的 nonce 校验与消费：

```php
$nonceB64 = (string)($req['nonce'] ?? '');
$nonceRaw = base64_decode($nonceB64, true);
if ($nonceRaw === false || strlen($nonceRaw) !== 32) { /* 400 */ }

// 待用记录按 (nonceId, deviceId, nonceRaw, exp) 保存。
$row = $store->get($req['nonceId'] ?? '');
if (!$row || $row['deviceId'] !== $req['deviceId'] || $row['exp'] < time()) {
    http_response_code(401);
    header('Content-Type: application/json');
    echo json_encode(['error' => 'bad_nonce']);
    exit;
}
if (!hash_equals($row['nonceRaw'], $nonceRaw)) {
    http_response_code(401);
    header('Content-Type: application/json');
    echo json_encode(['error' => 'bad_nonce']);
    exit;
}
$store->delete($req['nonceId']); // 消费一次

// 之后由 deviceId 关联用户，返回 Clash YAML（text/yaml）。
```

账号到期或设备吊销：

```php
http_response_code(403);
header('Content-Type: application/json');
echo json_encode(['error' => 'revoked']);
```

网关退役：

```php
http_response_code(410);
header('Content-Type: application/json');
echo json_encode(['error' => 'gateway_retired']);
```

## 14. 联调自测

跑通参考服务端，走完一次端到端：

1. 起服务（[`deploy/gateway/`](../../deploy/gateway/) 下的 `deploy.sh` 或 `docker compose up`），并把 `PUBLIC_ORIGIN` 设成要写进发现文件的网关 origin。
2. 建账号并绑定订阅 URL：

   ```bash
   cpx-admin add-user alice https://origin.example.net/sub/abc --limit 3
   cpx-admin list-users
   ```

3. 用 `scripts/plugin/gen-cpx.mjs` 生成指向网关 `/oauth/authorize` 的描述文件。
4. 在 Web UI 导入该 `.cpx`，完成登录，确认生成了订阅。
5. 核对线上行为：

   - `/enroll` 返回 2xx，`cpx-admin list-devices alice` 能看到新的 `deviceId`。
   - `/challenge` 返回 44 字符标准 base64 的 `nonce`，以及不超过 64 个可见 ASCII 字符的 `nonceId`。
   - `/config` 返回可解析为对象、含 `proxies` 或 `proxy-providers` 的 Clash YAML。
   - 重放同一个 `/config` 请求体会失败并返回 `401 bad_nonce`。
   - 删除插件后，`cpx-admin list-devices alice` 中该设备消失。
   - 设置 `RETIRED=true` 后，`/challenge` 与 `/config` 返回 `410 gateway_retired`。

客户端侧协议单测在 `src/main/resolve/plugin/*.test.ts`；网关侧单测在 `deploy/gateway/src/*.test.mjs`。

上游的签名测试向量（`src/main/resolve/plugin/__fixtures__/sign-vectors.json`）在本版中不存在，也没有任何测试或检查项依赖它。

## 15. 上线检查

`.cpx`：

- [ ] `magic`、`v`、`spec`、`loginUrl`、`provider` 字段符合第 3 节。
- [ ] `loginUrl` 是 authorize 端点，不带 query、fragment、userinfo。
- [ ] `provider.icon` 如有提供，使用允许的 data URI 格式，大小不超过限制。
- [ ] 描述文件以下载形式发布，不宣传任何深链。

登录域名：

- [ ] `/.well-known/cpx-gateway` 返回合法 JSON。
- [ ] authorize 允许 `http://127.0.0.1:<random-port>/callback`。
- [ ] 登录成功后 302 回调，带 `code` 和原始 `state`。
- [ ] `code` 一次性、TTL 不超过 60 秒。
- [ ] `code` 记录了 `username`、`redirect_uri`、`client_id`、`code_challenge`。
- [ ] authorize URL 能被"同时也能访问客户端所在机器 `127.0.0.1`"的浏览器打开（同机、隧道，或有明确替代方案）。
- [ ] 登录尝试有限流。

网关：

- [ ] `gateway` 是 `http`/`https` origin，无 path、query、fragment、userinfo。
- [ ] 四个 endpoint 都是相对路径，不含反斜杠、query、fragment。
- [ ] `/enroll` 一次性消费 code，校验 PKCE、redirect_uri、client_id，并执行设备数上限。
- [ ] `/challenge` 发放 32 字节随机 nonce，标准 base64，短 TTL，待用池有上限。
- [ ] `/config` 校验并消费 nonce，返回 Clash YAML。
- [ ] `/revoke` 校验并消费 nonce，幂等解绑。
- [ ] 账号到期、设备吊销返回 `{"error":"revoked"}` 或 `{"error":"device_revoked"}`。
- [ ] 网关退役返回 HTTP `410` 或 `{"error":"gateway_retired"}`。

编码和兼容：

- [ ] 服务端不要求请求签名（`devicePubKey`、`sig`、`ts`、`op` 均不使用）。
- [ ] `nonce` 使用标准 base64，带 padding，解码后为 32 字节。
- [ ] PKCE 字段使用 base64url，无 padding。
- [ ] `/enroll` 对 `redirect_uri`、`client_id` 逐字节比对。
- [ ] 隐藏 origin 始终不下发给客户端。

## 16. 常见问题

### 客户端一直重试，不提示重新登录

通常是服务端只返回了 `401` 或 `403`。需要在 JSON 响应体中返回：

```json
{ "error": "revoked" }
```

或：

```json
{ "error": "device_revoked" }
```

### nonce 校验失败（401 bad_nonce）

按顺序检查：

1. `nonce` 是否为标准 base64、是否带 padding、解码后是否正好 32 字节。
2. 比较时是否用了常数时间比较（`hash_equals` / `timingSafeEqual`）。
3. 是否在 `/config` 之前真的调过 `/challenge`，且 nonce 未被消费过。
4. 客户端每次 `/config`、`/revoke` 都会新领 nonce，不要复用同一个 nonce 应答两次。

### challenge 返回 429 too_many_nonces

该设备的待用 nonce 达到上限（默认 8）。客户端正常情况下一次只用一个 nonce，出现堆积通常是客户端反复失败重试、或服务端 nonce 没有随消费清理。

### authorize 拒绝回环重定向

`redirect_uri` 是 `http://127.0.0.1:<random-port>/callback`，端口随机。按 scheme、host、path 校验即可，不要固定端口，也不要要求 HTTPS。

### 用户在服务端登录成功，客户端却一直不返回

回调打到了浏览器所在机器的 `127.0.0.1:<port>`，而监听在客户端所在机器上。确认浏览器与客户端同机，或已把该端口从浏览器侧转发到客户端侧。

### 网关发现失败

检查 `gateway` 是否为 `http(s)` origin，不能写成 `https://gw.example.com/base`，也不能带 `?`、`#`、userinfo。内网 IP 和 `localhost` 是允许的。

### endpoint 拼接失败

`endpoints.*` 必须是 `/enroll` 这类相对路径。不要写绝对 URL、`//host/path`，也不要包含反斜杠。

### `/config` 返回后客户端仍然更新失败

成功响应必须是 Clash YAML。客户端要求 YAML 可解析为对象，并且包含 `proxies` 或 `proxy-providers`。返回 JSON、HTML、空 body 或非 Clash 配置都会被视为瞬时失败。

## 17. 日志

- authorize `code`
- `code_verifier`
- nonce 和 nonceId
